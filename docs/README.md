## 二、三条阅读路径

### 路径 A · 我只是想搞明白这东西在干什么（10 分钟）

```
README.md  →  01-background.md §1-§2  →  02-architecture.md §1（系统上下文图）
```

读完能答：这是个什么项目、服务什么业务、跟谁交互。

### 路径 B · 我要在这上面加东西（1 小时）

```
02-architecture.md §2-§4（分层与组件职责）
  → 03-tech-design.md §3-§4（状态契约与图组装）
  → 03-tech-design.md §7（四个任务怎么实现）
  → 03-tech-design.md §9.3（新增任务的三个改动点）
```

前提：先跑通 `pytest -q test`（7 项，不需要凭据）。

### 路径 C · 我要把它跑起来（半天）

```
04-runbook.md §1（凑凭据清单）
  → §2（八步部署，每步都有验证）
  → §5（遇到问题先查故障表）
```

部署最容易卡住的地方是凭据权限和持久盘，两处都在 §1 与步骤 6 里单独标注了。

## 三、文档编写约定

### 3.1 内容归属（写之前先判断放哪）

| 内容类型 | 放哪 | 判断标准 |
|---|---|---|
| 项目是什么、为什么做 | `README.md`（简短）+ `01-background.md`（详细） | 回答"为什么" |
| 结构与取舍 | `02-architecture.md` | 回答"为什么这样搭"，含架构图与决策记录 |
| 实现与坑 | `03-tech-design.md` | 回答"怎么做的"，含代码片段 |
| 操作步骤 | `04-runbook.md` | 回答"怎么执行"，可照着做 |
| 计划与进度 | `05-roadmap.md` | 回答"什么时候做、做到哪了" |
| 待评审的改造方案 | `06-event-driven-resume.md`（触发与通信）、`07-graph-patterns.md`（图结构与模式）、`08-agent-first-design.md`（tool 化与单图闭环） | 回答"这次要怎么改"；**评审通过并实施后，内容合并进 02/03/04，本文件删除**，避免同一主题两处留档 |
| 名词 | `glossary.md` | 单词级解释 |

**一条硬规则：同一主题只写一份，其他地方引用链接。** 发现两处都在讲同一件事，删掉一份——重复的内容一定会不同步，而不同步的文档比没有文档更糟。

### 3.2 写作要求

- **先给结论，再给理由**。每节第一段就回答本节标题提出的问题。
- **图和表优先于段落**。流程用 mermaid，对照用表格，散文只用于讲因果。
- **数字优先于形容词**。写"每日 ≤5 页"而不是"控制在合理范围"；写"$10-15/月"而不是"成本较低"。
- **代价必须写**。只讲好处的决策记录等于没写。
- **代码片段必须来自仓库**，不能手写"示意代码"冒充实现。片段太长就截关键行并注明文件。

### 3.3 图表规范

- 全部用 **mermaid**（GitHub 原生渲染，改起来是文本 diff）
- 架构图用 `graph TB` / `graph LR`，流程用 `flowchart TB`，时序用 `sequenceDiagram`，状态用 `stateDiagram-v2`
- 节点文字用中文，代码标识符（文件名、变量名）保持英文原样
- 每张图下面必须有一句"这张图在说什么"，不能只有图

### 3.4 更新触发条件

改了代码后，按这张表检查文档是否要同步：

| 代码改动 | 需要更新的文档 |
|---|---|
| 新增/删除任务 | `05-roadmap.md`、`03 §7`、`README` 的能力表 |
| 改 cron 时间 | `04 §4.1`、`README` 的能力表 |
| 改 D1 表结构 | `03 §8`、`migrations/` |
| 改环境变量 | `04 §3`、`.env.example`（三处必须一致） |
| 改红线规则 | `03 §7.4`、`05 §6`、`test/` 的单测 |
| 改架构（换框架/换存储） | `02` 的 ADR 新增一条，**旧的 ADR 保留并标注"已废弃"** |
| 阶段推进完成 | `05` 的状态列与环境相关的待办勾选 |

### 3.5 版本与变更

文档头部统一带版权与协议标识。结构性调整（例如把原先单份技术方案拆成 01-05 + 术语表）在提交信息里说明原因，不写在文档正文里——正文只反映"现在是什么样"。
