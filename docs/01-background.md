# 01 · 背景：toolara.dev 是什么，为什么需要这个 Agent

> 本文写给**第一次接触这个项目、但从没见过 toolara.dev 的人**。
> 读完你应该能回答：这个站群是干什么的、靠什么活着、一个人的运营卡在哪里、为什么非要做个 Agent。
> 不需要任何前置知识；涉及的名词见 [术语表](glossary.md)。

---

## 1. 一句话

**toolara.dev 是一个免费的英文在线小工具集合**，由 33 个互相独立的子域组成，每个子域只做一件事：一个计算器，或一个 AI 生成器。

- 主站：<https://toolara.dev> —— 汇总入口
- 子站示例：`paypal.toolara.dev`（算 PayPal 手续费）、`sourdough.toolara.dev`（算酸种面包水合率）、`music.toolara.dev`（用一句话生成一首完整歌曲）

主站自己的描述是：

> 32 free, fast, privacy-friendly online tools in two families: **calculators** for health, money, home, crafts and baking, plus **AI generators** for writing, images, music, audio and business.

33 个子域里减去一个内部工具（选题雷达，不对外），正好 32 个对外产品，与这句描述对得上。

**用户是谁**：英语国家的普通人。想算 Etsy 抽成多少、想知道华盛顿特区工资到手多少、想给播客写节目笔记、想给商品配一段文案。他们从 Google 搜一个具体问题进来，用完就走，不需要注册。

**怎么赚钱**：计算器站没有推理成本，纯前端算，靠自然流量；AI 站在免费额度之上提供付费订阅（`music` 站免费 3 首/月、单曲 60 秒，付费解锁更长时长），走 PayPal 收款。项目本身**不投广告买量**，流量几乎全部来自 Google 自然搜索。

## 3. 为什么是"33 个子域"这种形态

这个形态不是随手选的，每一条都对应一个具体收益。理解这些，才能理解 Agent 为什么必须按现在的样子设计。

### 3.1 一个关键词一个站

与其做一个"万能工具箱"大站，不如把每个搜索意图拆成独立产品：搜 `paypal fee calculator` 的人，落地页就是纯的 PayPal 费率计算器，没有导航干扰、没有其他工具分散权重。

对 SEO 的好处是**页面少而深**：一个站通常只有首页 + 多语言版本 + 少量内容页，内链结构极浅，爬虫抓取效率和主题相关度都高。

### 3.2 独立子域，而不是子目录

同样的工具如果放在 `toolara.dev/paypal-fee/` 下，所有工具会共享一个域名的历史与风险。拆成子域后：

- 每个站是 **GSC 里一个独立的资源**，收录问题、手动惩罚、算法更新影响都不会串到别人身上
- 每个站有独立 sitemap、独立 robots.txt、独立 OG 图与 favicon
- 哪天要卖站、下线、换技术栈，互不影响

代价是**权重不共享**，新子域等于从零开始——这也是为什么这个项目极度依赖内容页产出（见 3.4）。

### 3.3 独立仓库，独立构建

每个子站对应一个 GitHub 仓库（`ai-music-generator`、`paypal-fee-calculator`…），push 后由 Cloudflare 自动构建部署。仓库名 = Worker 名 = 本地目录名，三者一致。

好处：改一个站不用碰其他站；30+ 仓库并行构建，某个仓库构建失败只影响它自己。
代价：**没有任何"批量操作"能力**——想给 33 个站同时加一个页面或改一处文案，只能逐个仓库提交。这正是 Agent 要接手的第一类工作。

### 3.4 统一入口，但只有一层

所有子域都绑定在同一个 Worker（`tool-proxy`）上，由它做统一分发。这一层只做**跨站共享的事**，不做业务逻辑：

| tool-proxy 负责 | 说明 |
|---|---|
| 域名 → 站点转发 | 查表后经 service binding 转给对应 Worker，binding 缺失直接 503 并打日志（不静默降级） |
| 动态 robots.txt / sitemap.xml | 按站点路径清单生成，不落静态文件 |
| OG 图 | 统一 1200×630；自带品牌图的站单独放行 |
| 埋点注入 | 给每个 HTML 响应注入 `/_ev.js`，前端事件 POST 到 `/_ev` 写 D1 `events` 表 |
| Google 轻登录 | 11 个 AI 站共用一套 OAuth 校验，前端只存 localStorage |
| 旧路径 301 | 子目录改子域期间的临时兼容，稳定后整体删除 |

这层是**只读的真相来源**：Agent 不改它，只读它产出的 `events` 数据和站点路径清单。

### 3.5 边缘部署，零服务器成本

全部跑在 Cloudflare Workers 上，没有传统服务器：

- 静态站：Workers 静态资源托管
- 有状态功能：D1（SQLite）、KV（配置与缓存）、R2（封面图等文件）
- AI 能力：MiniMax / Flux 等第三方 API；Cloudflare Workers AI 只用在小流量场景

成本结构上，除了 AI 站按调用付费，其余站点的边际成本接近零。这让"养 33 个站观察哪些能长起来"成为一个人能承受的策略。

## 4. 流量与收入的现实

理解这一点，才知道 Agent 该优化什么。

- **流量结构**：绝大多数来自 Google 自然搜索，英文为主；部分计算器站做了 8 种语言（en / zh / zh-tw / ja / ko / de / ru / es）承接对应语区搜索
- **访问深度极浅**：工具站是典型的"搜到 → 用完 → 关掉"，会话时长以秒计。所以转化路径必须一屏内完成
- **收入的唯一来源**：`music` 站的订阅。其余 32 个站是流量与品牌资产，不直接收钱
- **不能买量**：单人项目，付费流量打不正 ROI，全部依赖自然增长

由此推出两个判断，它们直接决定了 Agent 的能力边界：

1. **杠杆点在"页面数量 × 收录率"**，而不是"页面设计"。多一个被收录的长尾词页面，就多一条免费流量入口。所以 Agent 的第一优先级是**持续产出能收录的内容页**，而不是重做 UI。
2. **数据必须被读**。自然搜索流量变化缓慢、信号微弱，单看某天没意义；必须按周看趋势、看"有展示没点击"的页面。人不会每天去看，机器会。

## 5. 一个人运营，卡在哪

这是本项目的立项理由。以下是站长实际每周要做的运营工作：

| 工作 | 现状 | 每周耗时（估） | 能否自动化 |
|------|------|--------------|-----------|
| 找选题 | `radar` 已经能扫 Suggest / Trends / SERP 并打分 | 1-2 h | 数据已就绪，**缺"决定后用起来"** |
| 写内容页 | 纯手工，一个页面 40-90 分钟 | 3-6 h | ✅ 结构化生成可自动化 |
| 上线（git → CF 构建 → 校验） | 手工 push、手工等 check run、手工看线上页面 | 0.5 h | ✅ 完全确定性流程 |
| GSC 提交与收录跟踪 | 手工提交 URL、隔几天翻后台 | 1 h | ✅ 有官方 API |
| 看数据、想对策 | 想起来才看，看了也难下结论 | 0-2 h | ✅ 可 LLM 结构化解读 |
| 外链机会 | 手工刷 Reddit / Dev.to，看到合适的记下来 | 2-3 h | ⚠️ 发现可自动，**发布不能自动** |
| 社媒推广 | 手工排期、手工做素材、手工发 | 2-4 h | ⚠️ 排期与素材可自动，**发帖不能自动** |
| **合计** | | **10-18 h / 周** | |

瓶颈很清楚：

- **不是缺想法，是缺执行带宽**。`radar` 已经能告诉人"这个词值得做"，但从"值得做"到"页面上线"中间有 5 个手工步骤，实际转化率极低。radar 里 `verdict=做` 的词长期堆着没有下文，这是最刺眼的浪费。
- **不是缺数据，是缺解读**。D1 的 `events` 表每天在写，GSC 也有数据，但没人每天看。信号弱、维度多，人肉看只会得出"大概还行"这种无用结论。
- **不是不想做外链和推广，是风险不允许自动化**。Reddit / HN / X 的账号都是长期养号资产，一次批量发帖就可能全废。这类工作只能"机器准备、人来发"。

一句话总结缺口：**感知层（radar）和执行层（33 个站）都已经建好了，中间那层"判断与调度"是空的，全靠人肉当胶水。**

## 6. 为什么不直接"再做一个更好的工具"

被考虑过、并被否掉的方向：

| 方案 | 为什么不做 |
|------|-----------|
| 做一个大而全的 AI 运营 SaaS | 目标是自己一个站群，不需要多租户；引入账号体系与计费反而拖慢 |
| 把逻辑塞进 Workers | Workers 无长驻进程、无持久化图状态；Workers AI 是账户级 10k neurons/天，出图站已占 82%，重 LLM 会挤爆额度 |
| 纯 workflow 脚本（无 LLM） | 内容生成与数据解读必须用 LLM；硬编码规则写不出可读的页面 |
| 全自动外链 / 全自动发帖 | 平台 ToS 与封号风险，账号是资产，不能赌 |
| 直接买现成 SEO 自动化工具 | 只能覆盖"关键词 → 文章"一段，接不上自己的 D1 埋点、CF 构建流水线、radar 打分体系；且多为 SaaS 订阅，数据要出境 |

结论：需要的是一个**跑在自己基础设施旁边、能读写自己数据、但把不可逆动作交还给人**的常驻 Agent。这就是 `site-agent`。

## 7. 已有资产盘点（Agent 依赖什么）

| 资产 | 位置 | Agent 怎么用 |
|------|------|-------------|
| `radar` 候选词 | `radar.toolara.dev`，D1 `candidates` | 只读：取 `verdict=做` 的词与其 SERP 数据 |
| `events` 埋点 | tool-proxy 写入 D1 | 只读：按天/站/页聚合 |
| 33 个子站 | 各自 GitHub 仓库 | 只写：新增 HTML 文件后 push |
| CF 构建流水线 | GitHub → Workers Builds | 只读：轮询 check run 状态 |
| D1 / KV | Cloudflare | 读写：台账三张表 + `agent:` 前缀的熔断/去重键 |
| GSC | Google Search Console | 读写：读展示/点击/排名，提交 Indexing |
| Resend | 邮件服务 | 写：日报、告警、审批请求 |

**明确不碰的东西**：tool-proxy 的路由与埋点逻辑、radar 的采集 cron、各站现有页面与样式。Agent 只在边缘新增，不改存量——这条边界写在 [02-architecture.md §7](02-architecture.md#7-与既有系统的边界)。

---

## 8. 读完这篇，你应该知道

- toolara.dev 是**一个人维护的 33 个免费英文工具站**，靠自然搜索流量，只有 `music` 站收费
- 站群的形态（独立子域 + 独立仓库 + 统一代理）决定了运营工作天然是"33 份重复劳动"
- 真正的瓶颈不在想法或数据，而在**从"知道该做什么"到"做完上线"之间的执行带宽**
- 所以这个 Agent 的定位是：**补上感知层与执行层之间缺失的判断与调度层**，并且把不可逆动作交还给人
